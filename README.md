# Anaesthesia digital twin on VitalDB

A digital twin of a patient under total intravenous anaesthesia (propofol and remifentanil by
TCI pump). It replays a recorded [VitalDB](https://physionet.org/content/vitaldb/1.0.0/) case as if
live, and every 30 s it:

- estimates the drug concentrations no monitor shows (pharmacological expert models);
- forecasts MAP, BIS and heart rate 1 to 10 min ahead, and warns of hypotension (MAP < 65 mmHg for
  at least a minute) before it starts;
- gives the probability that the anaesthetist will lower or raise each drug's target, the setting
  they would likely choose, and that change's expected effect.

The plan this follows is `Anaesthesia Digital Twin Project Plan.pdf`.

`data/` and `models/` are not in git: every result is rebuilt from the dataset with the commands
below. A training run's folder `models/<run>/` holds `models.joblib` (forecasters and suggesters),
`metrics.json` (all test metrics), `config.json` (the config and cohort it was trained with) and
`test_cases.json` (the held-out cases); `dte effects` adds `effects.parquet`. The results in
`docs/results.md` are from run `sixth`.

## Setup

Needs [uv](https://docs.astral.sh/uv/) and Python 3.14 (uv installs it), and git (PAS is
installed from GitHub, see ADR 0003). Sized for 16 cores and 32 GB RAM.

```bash
uv sync
```

VitalDB is cached under `data/vitaldb` (or `VITALDB_CACHE_DIR`). Files are fetched on first use;
the cohort tools need the whole dataset (~95 GB):

```bash
uv run vitaldb-cache download            # everything, in the foreground
uv run vitaldb-cache download 45 17      # specific cases
./download_vitaldb_daemon.sh             # everything, as a background systemd user service
tail -f data/vitaldb-download.log
```

```python
from digital_twin_engineering import vitaldb_cache as vdb

clinical = vdb.table("clinical_data")                     # pandas DataFrame
hr = vdb.load_case(1, ["Solar8000/HR"], interval=1)       # numpy array, 1 s grid
vf = vdb.load_vital(1)                                    # full vitaldb.VitalFile
```

## Verifying it works

Each step needs more data and time than the one before.

1. **Unit tests**, seconds; with case 45 downloaded also the end-to-end twin tests:
   ```bash
   uv run vitaldb-cache download 45
   uv run pytest
   ```
   `test_live.py` checks that the twin, fed raw records one by one, sees exactly what the offline
   pipeline computed (so nothing uses the future); `test_service.py` sends a case through an MQTT
   broker to the twin service and on to an InfluxDB-shaped endpoint.

2. **Smoke run**, minutes, after the full download: index the dataset once, then train on 12 cases
   and replay one through the twin.
   ```bash
   uv run dte inventory                                        # once, ~12 min
   uv run dte train configs/smoke.yaml cohorts/smoke.yaml --run smoke
   uv run dte replay 13 --run smoke
   ```

3. **Full run**, as for `docs/results.md` (1,585 cases; the first build takes hours, mostly PAS;
   later builds reuse the caches; training ~75 min):
   ```bash
   uv run dte dataset configs/default.yaml cohorts/tiva-artline.yaml
   uv run dte dataset configs/default.yaml cohorts/tiva-artline.yaml --perturbed
   uv run dte train configs/default.yaml cohorts/tiva-artline.yaml --run sixth
   uv run dte replay 17 --run sixth                             # a test patient through the twin
   uv run dte verify configs/default.yaml cohorts/tiva-artline.yaml   # experts vs pumps and vitals
   uv run dte effects --run sixth                               # what-ifs vs the clinicians' changes
   ```
   Compare `models/sixth/metrics.json` with the tables in `docs/results.md`; reruns differ by
   about 0.003 at most (LightGBM threading).

4. **Live stack**, see below.

## Pipeline

```bash
uv run dte coverage                           # share of cases with each channel
uv run dte explore map bis hr propofol_dose --by department optype   # largest consistent groups
uv run dte cohort cohorts/tiva-artline.yaml   # resolve and freeze a cohort's case list
uv run dte replay 17 --run sixth --out decisions.parquet   # the twin's decisions over a case
```

From raw tracks to decisions, each stage cached per case under `data/derived/`, keyed by its
config (`stages.py`; bump `VERSIONS` there when a stage's code changes its output):

| Module | Does |
|---|---|
| `vitaldb_cache`, `patients` | the dataset on disk; patient covariates and case phases from the clinical table |
| `inventory`, `cohort` | which cases have which tracks and were given which drugs; cohort YAMLs and the explorer |
| `channels` | tracks -> channels on a causal 1 s grid with staleness; pump volumes -> doses; training-time sensor faults |
| `experts` | PAS and AnestheSIM stepped through each case: concentrations, model BIS/MAP/HR; pre-dose baselines; online calibration; what-ifs on demand |
| `labels`, `targets` | hypotension events, interventions (TCI target changes), forecast targets (add vitals in `TARGETS`) |
| `features`, `dataset` | decision-point rows: windowed features, covariates, phase, labels |
| `forecasting`, `suggestion` | one LightGBM per (target, horizon); per-drug intervention suggesters |
| `splits`, `evaluation`, `pipeline` | patient split, baselines, calibration, metrics; `train` writes `models/<run>/` |
| `verification` | expert fidelity: Ce against the pumps' own models, BIS/MAP against measured |
| `effects` | validation: what-ifs against what followed the clinicians' target changes |
| `live` | the twin (raw records in, decisions out), the replayer, the twin service |

## Live stack

Replayer -> Mosquitto (MQTT) -> twin service -> InfluxDB -> Grafana, as in the project plan.
Message formats are in `live/messages.py`, what the service writes in `live/service.py`.

```bash
RUN=sixth docker compose up -d --build        # broker, database, Grafana, twin service with models/sixth
docker compose run --rm replayer 17           # replay case 17 at 30x (--speed, --until, --start)
# Grafana: http://localhost:3000 (admin/admin), dashboard "Anaesthesia twin"; pick the case at the top

# or without Docker for the Python parts (a broker and InfluxDB still needed):
uv run dte serve --run sixth --host localhost --influx http://localhost:8086
uv run dte publish 17 --run sixth --speed 30
```

The dashboard shows each forecast where it comes due, drawn dashed over what was measured; the
hypotension risk and alerts; estimated drug concentrations against the pumps'; the suggestions with
their expected effects; unexplained deviations; and fidelity so far. Runs trained before the alert
threshold was saved (`fifth` and older) need `ALERT_THRESHOLD=0.575`. After editing
`grafana/dashboard.py`, run it to regenerate `grafana/dashboards/twin.json`.

## Status

- Offline pipeline, models and validation: done; results and limits in `docs/results.md`.
- Live stack: the Python side is tested end to end through an MQTT broker. The InfluxDB queries and
  the Grafana dashboard have not yet run against a live InfluxDB and Grafana: bringing up
  `docker compose` and replaying a case is the check still to do.
- The suggesters imitate this hospital's practice; they don't say what is optimal. The what-ifs'
  BIS effects hold against observed target changes, MAP effects only in direction, HR effects not
  at all (`docs/results.md`, "Do the what-ifs hold?").
