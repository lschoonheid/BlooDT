1  Summary

The project is a digital shadow of one patient under total intravenous anaesthesia (TIVA). It replays real VitalDB cases. It estimates drug concentrations that a monitor cannot show. It forecasts MAP, BIS and HR, and it warns of hypotension. It also suggests a change of the propofol or remifentanil target to the clinician.

The code is one Python package, src/digital_twin_engineering, with about {{TOTAL_LINES}} lines. One command line tool, dte, runs all steps.

The architecture has three parts:

  1. Offline pipeline. It reads VitalDB cases, puts the signals on a causal 1 s grid, runs mechanistic expert models, and makes one row per decision point. Then it trains LightGBM forecasters and suggesters and evaluates them against simple baselines.
  2. Stage cache. Each stage writes its result per case to data/derived/<stage>/<config hash>/. A change of the configuration computes only the stages that the change touches.
  3. Live twin. The class live.twin.Twin receives raw records one by one. It uses the same functions as the offline pipeline, so it sees the same features. The MQTT, InfluxDB and Grafana services are only an outline at this time.

The main rule of the design is causality: a feature at time t uses only data that was known at time t. Many parts of the code exist for this rule: the grid with staleness, the dose counter, the pre-dose baseline and the test that compares the live twin with the offline grid.

2  Goal and scope of the twin

Source: Anaesthesia Digital Twin Project Plan.pdf (12 Nov 2026), README.md and GLOSSARY.md.

  • The anaesthetist keeps the patient unconscious (BIS 40 to 60) with propofol and remifentanil.
  • These drugs also decrease the blood pressure. MAP below 65 mmHg is related to organ damage after surgery.
  • The twin is a digital shadow: its advice goes to a person, not back to the pumps.
  • The data is VitalDB: 6,388 surgical cases with monitor, BIS and infusion pump tracks.
  • The plan gives these priorities. Must: replay → MQTT → twin → InfluxDB → Grafana, drug model with BIS prediction, hypotension warning 5 min ahead, fidelity panel. Should: online calibration, several rooms. Could: what-if panel, ML correction of the drug model.

4  Layers of the code

The figure shows the modules in layers. A layer uses mostly the layers above it. Exception: config.py reads channels and experts to find all the channels that the experts need.

entry points data access signals and case sets experts and labels rows and learning live

DetailWhat each layer does
  • Entry points. cli.py parses the sub-command and calls one function of a lower module. It has no logic of its own.
  • Foundation. vitaldb_cache downloads PhysioNet files on first use and checks them with SHA256SUMS.txt. patients reads clinical_data (age, sex, height, weight, BMI, ASA). stages keeps per-case results on disk. config turns a YAML file into a frozen Config dataclass and makes the cache keys.
  • Signals and case sets. channels defines 23 channels and the causal grid. inventory scans all cases once. cohort selects cases from YAML criteria.
  • Experts and labels. The expert models step through a case one second at a time. labels and targets look at the full case (also the future), so they make only training labels.
  • Rows. features makes the forecaster inputs with look-back windows. dataset joins everything into one row per decision point.
  • Learning and evaluation. Forecasters, suggesters, the patient split, the metrics, the ablation and the expert fidelity check.
  • Live. The twin and a replayer. They reuse the modules above without change.

5.2  Clean rows and perturbed rows

dataset.case_rows(perturbed=True) takes the features from a frame with simulated sensor faults. It takes the labels from the clean frame.

The faults are in channels.Perturbation: an extra delay of 0 to 10 s per channel and about 4 dropouts per hour of about 30 s. They apply only to “level” channels (vitals), not to pump settings or doses.

The seed of a fault depends on the case and the channel name only. So the same channel gets the same fault, also when other channels change.

6  Key ideas in the code

6.1  Causal grid with staleness (channels.py)
  • A Channel has a name, a kind (level, setting or dose), a unit, a list of candidate tracks with a unit factor, a valid range and a maximum staleness.
  • resolve selects the first candidate track that the case has.
  • to_grid puts the raw records on the 1 s grid. Each cell holds the last value at or before that second. The code never interpolates.
  • Each channel gets a second column <channel>__staleness: seconds since the observation.
  • Values outside the valid range are removed first. Thus an artefact shows as a growing staleness.
  • When the staleness is more than max_staleness_s (300 s for most vitals), the value becomes NaN.

Why: interpolation uses the next observation, so it leaks the future. It also hides gaps that the live twin will see. (ADR 0002.)

6.2  Dose counter (channels.DoseCounter)

A pump records a cumulative volume (*_VOL, mL). The raw data has three problems:

  1. Small decreases of about 0.2 mL (jitter).
  2. Resets when a syringe or pump restarts, not always to zero.
  3. Single wild values, for example 249037.83 mL between two values near 13 mL.

The counter accepts a rise only if a pump can deliver it (maximum 1200 mL/h). It ignores small decreases. It keeps a large jump as “pending” until 5 more readings arrive. If the jump stays, the counter starts again from the new level (a re-base). If not, it ignores the jump.

Consequence: after a jump, the dose total becomes known up to 5 readings late. The grid uses the time when the value became known, not the time of the reading. The live twin uses the same counter, so offline and live agree.

On the grid, a dose channel holds the amount for each step (difference of the total), in mg or µg.

6.3  Expert models (experts/)

An expert follows the protocol Expert: name, inputs, signals, reset(covariates, step_s), step(inputs). experts.build(spec) makes an expert from a dictionary of the YAML file. The key kind selects the class.

KindClassModelsSignalsLookahead
pasPasExpertPython Anesthesia Simulator: Marsh_modified / Schnider / Eleveld propofol, Minto / Eleveld remifentanil, Bouillon / Eleveld BIS, VitalDB haemodynamicspropofol_ce, remifentanil_ce, bis, map, hr, coNo (too slow)
anesthesimAnestheSimExpertPort of AnestheSIM 1.0.0 (MATLAB): Schnider, Minto, Joachim norepinephrine, volatile effect sites; BIS surface greco/bouillon/minto; MAP separable or unifiedCp and Ce of each drug, volatile MAC, bis, map, hrYes, and what-if
  • Runner drives one expert one step at a time. It sets a missing dose to 0. The offline experts.run and the live twin use the same Runner.
  • With baseline: pre_dose, the expert takes the resting MAP and HR from the median of the observations before the first dose (experts/baseline.py). MAP comes from the cuff (NIBP), because the arterial line is often not ready before induction.
  • The AnestheSIM port uses an exact zero-order-hold matrix step (scipy.linalg.expm) in place of an ODE solver. This makes it fast.
DetailLookahead and what-if
  • At each decision point, the Runner asks the expert for its state after 120 s and 300 s. It holds each dose at its mean of the last 60 s.
  • The expert copies its state, simulates ahead, then restores the state. Columns: <expert>.<signal>@<h>.
  • With whatif: [0.8, 1.2], AnestheSIM also simulates each TCI target × 0.8, × 1 and × 1.2. Its own TCI controller (_tci_rate) steers the effect-site concentration to the new target, as a real TCI pump does.
  • The feature is the effect: what-if minus the × 1 scenario.
  • In the live twin, Runner.effect uses the same method for the suggested new setting.

6.4  Labels and targets (labels.py, targets.py)
  • Value target (map, bis, hr): the value one horizon ahead. The future observation must be fresh (staleness ≤ 10 s). Else the label is NaN.
  • Event target (hypotension): 1 if an event occurs at any time in (t, t + horizon]. An event is MAP (5 s median) below 65 mmHg for 60 s or more. Missing MAP never counts as low.
  • Intervention: a change of the TCI target that holds for 30 s or more and is 5 % or more. A short value while the knob turns (3 → 3.5 → 4) is not an intervention. A pump start is an intervention.
  • Suggestion label: the direction (decrease, hold, increase) and the new value of the first intervention in the 60 s after the decision point.

To add a vital as a target, add one Target to TARGETS and its name to targets: in the YAML.

7  Stage cache (stages.py)

Each stage writes one Parquet file per case:

data/derived/<stage>/<config hash>/<caseid:04d>.parquet
data/derived/<stage>/<config hash>/config.json      # the config that made the hash
StageKey (from Config)VersionContents
channelschannels_key: all channels, step, perturbation, seed2Grid of all channels and staleness
expertsexpert_key: one expert spec, its class version, step, perturbation, seed, lookahead2Signals of one expert (one folder per expert)
rowsrows_key: the two keys above, targets, horizons, decision interval, features, suggestion7Decision-point rows of one case
  • The hash is SHA-256 of the key and the stage version (12 hex digits).
  • The cache cannot see changes of the code. When a change alters a result, increase the number in stages.VERSIONS. Also increase the numbers of the stages that depend on it.
  • An expert class can have its own version (AnestheSIM has 1). A change then recomputes only experts of that kind.
  • A write goes to a .part file first and then moves. Thus parallel processes do not see half files.
  • inventory and cohort also write to data/derived/: track_inventory.parquet, drug_usage.parquet and the frozen cohort manifests.

8  Models, split and evaluation

8.1  Split (splits.py, pipeline.split)
  • The split is by patient (subjectid), never by row or case. 80 % of the patients train, 20 % test.
  • With a perturbation, half of the training patients come from the perturbed rows. Each patient is in the training set once.
  • The test has two sets: clean and perturbed (the same test patients with sensor faults).
  • Cross-validation uses GroupKFold by patient, 5 folds.

8.2  Two levels of models
  • forecasting.fit_with_out_of_fold trains one model per fold and predicts the rows of the patients that the model did not see. The suggesters train on these predictions. So they learn how much they can trust a forecast on a new patient.
  • Then a final forecaster trains on all training rows. It predicts the test rows.
  • LightGBM accepts NaN. Missing channels and experts that do not apply leave NaN.
  • The default parameters are in configs/default.yaml under model: (400 trees, learning rate 0.03, 30 % of the features per tree).
  • The regressor of the suggester clips the result: a decrease stays at or below the current setting, an increase at or above.

8.3  Evaluation (evaluation.py)

Each model has a baseline that does not learn:

ModelMetricsBaseline
Value forecasterMAE, RMSEPersistence (the current value stays)
Hypotension forecasterAUROC, AUPRC, sensitivity at 10 % alert rate, Brier, ECE; also on onsets only“MAP already low” (score = −current MAP)
Suggesterlog loss, AUROC per direction, ECE; MAE of the new settingClass prior; “keep the current setting”

8.4  Ablation and verification
  • ablation.run trains the forecasters again without one group of inputs: no experts, only one expert, no staleness, no covariates, no phase. Output: models/<run>/ablation.json.
  • verification.fidelity compares each expert with reality, per case, with Varvel metrics (MDPE, MDAPE, RMSE). Concentrations go against the pump's own TCI model (propofol_ce_pump). BIS and MAP go against the monitor. Only fresh values (staleness ≤ 5 s) during anaesthesia count.

9  Live twin (live/)
  • The replayer sends raw records, not grid values. The twin makes its own grid. Thus it sees the same data as the offline pipeline.
  • tests/test_live.py replays a case with a pump volume jump. It checks that the twin grid is equal to the offline frame.
  • The twin knows the phase times (anaesthesia start, surgery start and end) from VitalDB's EVENT track. In dte replay, they come from clinical_data.
  • replayer.load_run(run) reads models/<run>/config.json and models.joblib. So the twin uses the configuration of its training run.

AnswerWhat does “Model” mean in this table, and why is its value a number such as 12.09?

Short answer. The table does not list models. Each row is one question, and each cell is a score (an error or a quality value). “Model” is the score of the trained model. “Baseline” is the score of a simple rule that does not learn. For MAP, 12.09 means: the trained model's forecast of MAP 5 min ahead has an average error of about 12 mmHg.

The row “MAP RMSE at 5 min (mmHg)”, step by step.

  1. The “model” is the LightGBM forecaster for the target map at the horizon 300 s (y.map@300). Section 8.2 describes it.
  2. At each decision point of each test patient, the forecaster predicts the MAP 5 min later.
  3. The code then compares each forecast with the MAP that the monitor measured 5 min later. The difference is the error of that point.
  4. RMSE (root mean square error) is one number for all these errors: RMSE = √(mean of error²). Its unit is the unit of the target, here mmHg.
  5. Lower is better. RMSE = 0 means that every forecast is exactly correct.

The baseline “persistence” is the rule “MAP in 5 min = MAP now”. Its RMSE is 16.19 mmHg. The trained model has 12.09 mmHg. Thus the model decreases the error by about 25 % (from 16.19 to 12.09). This comparison shows that the model learned something useful: it is better than the simple rule.

Example with one decision point. MAP now is 80 mmHg. The monitor shows 72 mmHg 5 min later. The model forecast is 75 mmHg: its error is 3 mmHg. Persistence forecasts 80 mmHg: its error is 8 mmHg. RMSE collects such errors over all test points into one number.

The other rows use other scores.

RowScoreBetter whenBaseline rule
BIS RMSE at 5 minAverage error of the BIS forecast (BIS units)lowerBIS in 5 min = BIS now
Hypotension onset AUROCHow well the warning score puts the points before a hypotension above the other points (0.5 = random, 1 = perfect)higher“MAP already low”: lower MAP now gives a higher score

Where the numbers come from in the code. evaluation.forecaster computes "model": {"mae", "rmse"} and "baseline_persistence": {"mae", "rmse"}. pipeline.train writes them to models/<run>/metrics.json, under clean → y.map@300. docs/results.md copies them from the run fourth.

Important for the architecture: the ablation shows that the expert models add almost nothing to the forecast accuracy (BIS RMSE −0.02). The value of the experts is elsewhere: concentrations that no monitor shows, and the what-if effects.

16  Open items and observations

These items come from a read of the code and the plan. They are not bugs that a test showed.

  • The service layer is not ready. replay_mqtt raises NotImplementedError. docker-compose.yml has no replayer and no twin service. The plan puts “replay → MQTT → twin → InfluxDB → Grafana” in “Must”.
  • The plan and the code differ. The plan names PAS as the drug model. The code adds the AnestheSIM port, which gives the lookaheads and the what-if. The plan names a warning model. The code also has BIS, HR and MAP forecasters and intervention suggesters.
  • PAS has no lookahead. The config comment says that PAS is too slow for it.
  • The cache does not see code changes. A developer must increase stages.VERSIONS by hand. If not, old results stay in use.
  • Memory limit. The decision interval is 30 s, not 10 s, to fit the TIVA cohort in 32 GB of RAM.
  • Boluses are not visible. VitalDB gives only totals per case for boluses.
  • The suggesters copy one hospital's practice. They do not show what is correct.
  • Licence. PAS is GPLv3. AnestheSIM is MIT and its notice must stay in experts/anesthesim.py.
